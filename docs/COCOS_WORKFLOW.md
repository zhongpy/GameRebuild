# Cocos 工程与三端交付规范

适用范围：本工作区以 Cocos Creator 重建的游戏。首批平台为 H5、微信小游戏、Android；原始网页参考版本保持原引擎。

源包为 Unity 时，先执行 [Unity 游戏包重建规范](UNITY_REBUILD_WORKFLOW.md)，再按本文组织 Cocos 实现和平台交付。原包方法、Prefab 和动画证据决定移植语义；不能将 Cocos 工程可运行当作原版还原已完成。

所有产品默认竖屏，横屏须由用户额外指定。当前验收按阶段推进：先完成 H5 并交用户人工验证，明确通过后再进行微信小游戏链路验证，Android 最后。后续平台的接口边界提前保留，验证任务不提前执行。

## 版本和工具链

- 环境模板当前以 Creator 3.8.8 为初始基线；各独立项目在 project.config.json 中固定版本。工程版本字段和构建记录必须一致，不用 Dashboard 版本代替 Creator 版本。
- 引擎升级、渲染管线切换、物理实现替换作为独立变更验证，保留升级前构建结果。
- 记录依赖锁文件及 Creator、Node（如参与外部脚本）、JDK、SDK、NDK、CMake、Gradle/AGP 版本。项目执行时显式选择工具，不依赖机器上“最新”版本。
- 本机路径是环境信息，不写死进可复用业务源码。按项目/构建进程传入路径，避免改变全局 JAVA_HOME 或其他项目工具配置。

## 工程组织

每个游戏拥有独立 Git 仓库，项目计划和规则归本仓、原包在工作区 resources/。首次或换机先执行工作区 node tools/check-environment.mjs --write，读取本机配置；实际构建需核对项目版本约束。每个游戏建立独立 `projects/<game>/` 工程。使用 Creator 生成或从已验证同版模板建立真实工程，再验证编辑器能导入；不猜测 .scene/.prefab 序列化格式。

建议结构（按实际需要创建）：

```text
assets/
  scenes/                 # Boot、Game 等可编辑场景
  prefabs/                # 车辆、角色、UI
  art/                    # 转换后的模型、图像、材质
  audio/
  configs/                # 规则和关卡参数
  scripts/
    core/                 # 纯 TypeScript 状态和规则
    application/          # 用例编排、输入命令、流程
    presentation/         # Cocos 组件、镜头、动画、UI
    platform/             # H5、微信、Android 服务实现
    infrastructure/       # 资源、配置、存档序列化
settings/
native/                   # 若生成且含需要维护的原生源代码
build-profiles/           # 从该版本构建面板导出并核验的配置
```

依赖约定：core 不导入 `cc`、DOM、wx 或原生 SDK；presentation 将输入转为命令并展示状态；平台实现通过接口接入 application。先保留必要接口（存档、生命周期、平台能力），实际需要广告等功能时再扩充。

资源及 `.meta` 一起提交和移动，保护 UUID 和引用。保存源码、配置、场景、Prefab、材质、必要原生源、构建扩展及依赖锁；不提交 `library/`、`temp/`、生成 `build/` 等缓存。不要一概忽略 `native/`，其中可能包含人工维护的 SDK 接入代码。[工程结构说明](https://docs.cocos.com/creator/3.8/manual/en/getting-started/project-structure/index.html)

## 素材和行为

- 原始包只读，转换结果带输入哈希、工具版本、参数、输出路径及逻辑名映射。Cocos UUID 由真实资产导入产生。
- 图集保留原始尺寸、旋转、裁切偏移、边距、锚点；字体回退和栅格化分辨率纳入画面对照。
- 模型建立源空间到 Cocos 空间的变换约定；单独对照材质、渲染、包围体与规则碰撞。
- 规则层保存逻辑状态，渲染节点不是唯一状态来源；计时、随机和输入应可记录/回放，算法变更需原版证据支持。
- 不把 DOM、MSStart/FRVR 初始化和 Service Worker 带进通用玩法层。`wx.*` 与原生桥只在对应适配实现中使用。
- 存档有版本、默认值和迁移策略，三个平台分别验证；共用结构不等于自动跨平台云同步。
- 广告或登录未接入时返回明确的不可用结果；开发模拟要可识别，奖励仅按已确认的成功语义发放。

## 三端构建和验收

| 目标 | 构建与运行要求 | 重点验收 |
| --- | --- | --- |
| H5 | 初始用 Web Mobile；明确本地服务与最终部署资源路径 | 触控/鼠标、窗口适配、音频解锁、刷新存档、前后台 |
| 微信小游戏 | 独立构建配置；确认工具、AppID 和真机预览条件 | 安全区、触控、资源/分包、暂停恢复、存档、平台能力失败分支 |
| Android | 固定工具链和包名；先调试 APK，后按交付需求配置发行构建 | 安装启动、返回键、前后台、音频、触控、存档、目标 ABI |

AppID、包名等标识按实际项目配置；签名密码、密钥及 SDK 凭据走本地配置或发布环境，不写入通用技能与日志。开发构建、发布包和商店上架是不同交付项。

使用同版构建面板导出的 JSON 配置作为自动化起点。CLI 参数以对应版本为准；Creator 文档将退出码 36 定义为构建成功，不能只把 0 当作成功，也不能只依赖退出码：同时核对日志和产物。[命令行构建](https://docs.cocos.com/creator/3.8/manual/en/editor/publish/publish-in-command-line.html)

不直接修改生成 build 目录作为长期修复；可重复的差异保存在源码、构建扩展、版本化模板或需要维护的原生源码中。每次构建记录源码版本/清单、Creator 版本、配置、依赖组合、退出码、日志和产物路径。

每个平台独立记录：未验证 → 导出/构建通过 → 工具/浏览器运行通过 → 目标设备通过。编辑器预览不替代 H5 发布包，H5 成功不替代微信/Android；Android 导出工程不等于 APK 已编译和运行。

小场景和核心玩法里程碑先验证竖屏 H5；用户人工通过后按微信、Android 的顺序推进。性能记录包括设备、场景、首屏时间、包大小、内存和帧时间，阈值依据实测与目标设备确定。未定义指标时不得宣称性能达标。
