# Unity 游戏包重建规范

适用于从 Unity 发布包（WebGL、移动或桌面）重建可维护工程，以及修正既有重建的还原度。目标引擎、竖屏要求和平台阶段服从用户与项目约定。本规范不要求普通构建、文档修改重新逆向整包。

以原始资源、序列化结构、配置和实际执行逻辑建立实现依据，再用运行数据与画面验证。原始 C# 缺失时继续检查编译代码；不要把“尚未解析”写成“没有代码”或“无法恢复”。也不承诺反编译必然恢复完整原始工程。

## 1. 开始前确认范围

- 读取工作区/项目 AGENTS、项目配置和现有提取/验收记录。先复用可信产物，检查版本、输入哈希与覆盖范围；旧报告的“通过”只对其原范围有效。
- 确定本轮问题及相关系统：例如解锁、生产、波次转换、攻击命中或某个 UI 页面。先查影响当前问题的资源和方法，不要求先反编译整套引擎才做局部修复。
- 原包只读。解压、反汇编、反编译、转换和插桩写入 reference/、evidence/ 或项目忽略的 local/；脚本、工具版本、轻量证据索引归项目仓库。Python 只使用工作区 resolved.python 对应的专用 Conda 环境。
- 补充资源须记录来源、版本、哈希及适用范围。仅名称相同或能解析不证明同版本；原包与补包冲突时先调查，不静默用补包覆盖原数据。

## 2. 按实际代码类型选择路线

| 包内材料 | 应检查的内容 | 不可作为方法恢复结论的材料 |
| --- | --- | --- |
| 原始脚本或源码 | 入口、调用链、条件、状态与资源绑定，确认源码与运行包版本对应 | 未确认被调用的旧代码或测试分支 |
| Mono 托管程序集 | 具有真实 IL 的程序集、依赖和可用符号；方法体反编译后回查 IL 与调用处 | 只有类型名、签名或空方法的程序集 |
| IL2CPP 原生包 | 匹配版本/架构的原生二进制、metadata、注册信息与符号；建立方法到代码位置的映射 | 仅从 metadata 生成的 dummy DLL / 声明文件 |
| IL2CPP WebGL | 解压后的 WASM、metadata、加载器/胶水代码及可用符号；定位函数、函数表、间接调用和业务映射 | WASM section/export 清单、仅反汇编但未识别业务的函数，或把平台 SDK JS 当作游戏业务源码 |

记录 Unity/metadata 版本、包平台、代码格式、是否存在符号、已使用工具版本及兼容性结果。工具选择按这些证据确定，不假定某工具支持所有 Unity 版本；安装分析依赖时限定到工作区/项目环境，不升级游戏的引擎或替换原二进制。

**方法证据至少说明：** 源文件及哈希、所属模块/类型、方法 token 或其他标识、实际代码位置（如 WASM 函数索引/偏移或原生地址及基址规则）、映射依据、相关调用者/被调用者、关键条件与状态变化、验证方式及尚不确定之处。地址不适用时说明采用的源码或运行定位方法。

注意优化、内联、泛型共享、协程状态机和间接调用；不能用 metadata 方法序号直接冒充 WASM 函数序号。反编译伪代码也要核对常量、分支、调用点与原指令/运行结果。提取出方法名，不得将该方法状态记为“已还原”。

## 3. 恢复资源结构和配置

- 建立资产依赖图：场景、Prefab、组件、ScriptableObject、图集、字体、材质、Animator、AnimationClip、音频和 Addressables。保留跨文件引用、pathID/GUID 等原标识；64 位 ID 不经不安全的数值转换。
- UI 按原父子结构、RectTransform 锚点/pivot/尺寸、Canvas 缩放、布局组件、遮罩、排序及事件绑定重建。原坐标须先解算父级变换；不能直接把 localPosition 当屏幕位置，也不从截图手工拼一个相似页面代替可读取的结构。
- 资源缺类型树时，结合匹配的类型信息和序列化布局解析，核对长度、字段类型、引用与原字节；记录解析失败及其影响。完整消耗字节是必要的解析检查，不能单独证明字段语义正确。
- 建筑占格、触发器、碰撞盒、人口、出生点和路径分别恢复；美术包围盒不代替规则占格。“看起来是 2D”不能决定源游戏使用了哪种物理或坐标系统。
- 动画同时检查曲线、状态转换、参数、事件、播放速度、触发代码和反馈组件。恢复 AnimationClip 不等于恢复 Animator 状态机或动画与命中时机。
- 转换脚本记录输入哈希、对象路径、参数和输出映射，保持可重复；Cocos 资源与 .meta 一起维护，仍通过实际引擎导入，不猜测场景序列化格式。

### 批量转换与增量验证

- 从配置字段、序列化引用及已确认的运行加载规则生成资源清单，按角色/动画、静态场景、粒子/材质、UI、音频分类。共享引用去重，声明引用、已观察启用和仅静态发现分别标记；不能以命名相似猜绑定或认定缺包。
- 同一格式先验证代表样本，再批量转换所有相关候选。资源范围不受当前已实现关卡限制；不要重复逐关复制贴图、导出动画或提取同一套源对象。
- 缓存绑定源版本、相关原对象/图片哈希、转换工具/参数和输出哈希；输出丢失、损坏或来源变化时失效。按需加载的派生资源与玩法实现分开组织，复跑保留 UUID，并复用现有可信提取。
- 特殊格式按原因集中处理。例如动画路径冲突、多 Animator、未支持曲线、粒子/网格渲染、未知 Shader 属于不同适配问题；存在 Animator 不代表该预制体由精灵构成。单项失败保留定位与影响，不阻塞其他候选、不静默截断，也不发布半成品为可用资源。
- 批量验收检查源映射、层级/绑定、数值有效性、缺失图片/材质，以及实际引擎加载和代表时刻采样；保留共享控制器中无法绑定的状态。未解析状态不自动开放，成功预览不代表完整状态机、粒子或业务行为一致。
- 用项目既有工作表连接清单与异常，不为每关建立重复流程。资源转换按类型、玩法按共用机制、关卡按组合和进度边界验收；三者分开推进，避免逐关搬资源，也避免等待全资源完成才接已有证据充分的玩法。

## 4. 按系统建立行为证据

先追踪入口和生命周期，再实现对应的小闭环。优先核查用户报告的问题与影响玩法的边界：

- 解锁：初始化/静态构造、存档读取、页面入口及交易检查，区分“达到某关”和“通关某关”。
- 波次：开始、生产、暂停、死亡、结算、恢复和下一波的调用顺序；收入按哪个时刻的存活状态计算。
- 战斗：属性来源、成长/取整、攻速单位、动作事件、弹体到达、选敌、碰撞/避让、固定步/帧更新及时间倍率。
- 经济与存档：收益生成、显示、领取、重复保护、保存时机和恢复语义。不能让表现动画再次发奖。

不能凭变量名、枚举名、孤立数值、资源数量或一张截图确定算法和启用条件；例如名为 speed 的字段可能仍需方法上下文才能确定单位。

**遇到未知时：** 记录具体缺口、已尝试的方法/工具、失败证据、影响范围和下一条可执行路线。相同前提下重复截图或重复运行失败工具不算进展。继续不依赖该缺口的工作，不为等待整包逆向而停住所有任务；也不把关键未知悄悄改成默认规则。已有近似实现保留其标记，需临时方案时遵循用户/项目已授权的范围，不重复索要已给出的决定。

用户指定的改动（例如暂定解锁关卡）属于产品决策，记录授权与适用范围，不能写成原版证据；后来查到原值也不擅自覆盖该决定。

## 5. 运行验证与截图的用途

- 原版参考使用独立存档和真实输入，记录版本、初始状态、随机源/结果、时间语义、输入及可观测输出。优先对照事件序列、状态变化、数值和时刻；截图/录像用于核对画面、发现差异和补充观察。
- 截图不能独立证明未开放功能、精确公式、内部计时、碰撞规则或方法实现；静态代码中的路径也不能单独证明当前版本已启用它。
- 静态分析不足时，可在参考副本进行可追溯的调试/插桩探测，定位调用、参数、字段与事件；验证映射和探针对时序/随机的影响，保留未插桩对照。此类探测与自然游玩基线分别标记。
- 修改状态、跳过关卡、强制胜负或冻结时钟只能作为明确标识的实验；不能据此报告自然解锁、自然通关或原版正常行为。重建侧预置测试存档也必须隔离并标记。
- 对齐双方场景与前提；做不到完全相同则写明差异，不据此给出像素/时序一致结论。视觉容差应针对实际差异解释，不用任意放宽容差掩盖偏差。

## 6. 记录和验收口径

每个项目维护一份轻量恢复索引（可用 `docs/UNITY_RECOVERY.md` 或扩展现有同类文档），大体积转储/录像放本地 evidence。索引最少包含：

| 系统/问题 | 原版依据与可复现定位 | 证据类型 | 已确认规则/仍未知 | Cocos 对应实现 | 对照结果与下一步 |
| --- | --- | --- | --- | --- | --- |

证据类型分别标注：**原始源码、二进制方法、序列化配置、运行观察、推断、用户产品决策、未知**；可组合，不用单一“源码证实”掩盖只是字段或签名。方法条目补充第 2 节的映射信息。既有项目复用原记录，不为每次小改动机械复制整份报告。

分开报告四个维度：

1. **提取情况**：有哪些原始材料、哪些可读取、失败哪些；数量只证明覆盖量。
2. **功能实现**：重建中哪些路径可执行、哪些仍为近似/占位；不能由提取数量推断完成度。
3. **原版一致性**：原版预期的独立来源、输入、实际差异与通过范围。测试期望不能从待验证的重建实现生成，否则只是自洽测试。
4. **用户/平台验收**：具体版本、场景和平台；遵守项目 H5 → 人工确认 → 微信 → Android 的阶段要求。

规则测试应覆盖原版证据揭示的边界，而不只是重复实现公式。构建通过、自洽测试通过、素材恢复一致、可玩或用户首关通过，均不等于全游戏已还原。关键玩法仍依赖未经确认的推断或存在占位功能时，不标记“全功能重建完成”；对有意偏离原版的用户决定按其验收范围记录。

## Agent 任务提示模板

以下模板用于给后续 agent 明确当前任务；项目名、问题和阶段由实际上下文替换，不需要为每次任务创建额外文件。

> 在指定项目仓库处理当前 Unity 原包重建问题，先读取项目 AGENTS、配置、恢复索引以及工作区 Unity 重建规范与 unity-package-rebuild skill。
> 先查原资源/配置和相关方法；按包内实际代码类型建立可复现证据，区分方法签名、方法体、运行观察、推断与用户指定行为。
> 只实现本轮证据支持的闭环，未知项记录定位、尝试、阻碍及下一步；不要用截图猜规则，也不要为逆向整个引擎推迟已经证据充分的局部工作。
> UI/动画按原节点、布局、曲线与触发关系恢复；截图用于最终视觉对照。规则按原输入和状态序列验证，实验/插桩与自然游玩隔离。
> 资源按配置依赖和格式批量转换，使用输入/工具/输出哈希缓存并集中记录异常；玩法按共用机制推进，关卡作为集成验收边界，不逐关重复转换资源。
> 完成后分别报告提取、实现、一致性和人工验收状态，更新项目记录，遵守既定平台阶段与仓库边界。
