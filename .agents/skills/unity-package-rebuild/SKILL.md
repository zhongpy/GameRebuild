# Unity 原包重建

目标是基于原包证据建立可维护实现。原始 C# 不存在时继续调查编译代码；元数据、dummy DLL 和函数清单不能代替方法体。截图用于运行/视觉对照，不能替代可获取的资源结构或关键规则分析。

## 入口与范围

工作区从用户指定位置、REBUILD_WORKSPACE_ROOT 或本技能目录的 `../../..` 定位；显式读取工作区 AGENTS、projects.json 和项目 AGENTS、project.config.json、docs/REBUILD_PLAN.md，以及已有恢复索引。不假定独立项目会话自动加载父仓规则。

开始 Unity 重建或修正还原度时读取 [Unity 重建规范](../../../docs/UNITY_REBUILD_WORKFLOW.md)，它是本技能的详细流程与验收依据。只处理当前模块需要的步骤，不重复已有可信提取，也不要求先反编译整个引擎。

## 工作步骤

1. 核实源版本、哈希、实际代码类型及现有产物的覆盖范围。使用规范第 2 节选择 Mono / IL2CPP native / IL2CPP WebGL 路线，调查工具兼容性，保留失败原因。
2. 定位本轮问题的资源、配置和方法，形成可复现的行为依据。记录方法标识与代码位置、映射依据、关键分支和调用关系；不要把 token、方法序号或名称相似当作已完成地址映射。
3. 按规范第 3–4 节恢复结构及行为。UI 读取层级/锚点/组件；动画读取曲线/状态/事件及驱动逻辑；玩法确认时序、公式和边界。原包保持只读，工具输出写入独立目录。
4. 对静态不能判定的行为，按第 5 节选择运行跟踪或有标记的插桩实验，保留独立自然基线；记录探针对原行为的影响。不能用强制通关实验声称原版自然进度通过。
5. 实现有证据支持的局部闭环并对照。使用原版独立预期检查重建结果；源码自洽测试与原版一致性分开报告。目标为 Cocos 时继续遵守工作区 Cocos 工程规范和已有平台阶段。

## 未知项和交付

关键逻辑尚未定位时，记录具体尝试、阻碍、影响及下一条路线，继续其他可推进项。不要悄悄将推断作为正式规则；临时实现遵循用户/项目已授权范围。用户明确指定的暂定行为单列为产品决策，之后发现原值也不静默覆盖。

复用或建立项目 `docs/UNITY_RECOVERY.md`：按规范第 6 节链接源文件/对象/方法与本地证据，列出当前实现及差异。大体积反编译输出和录像不入规范仓库；可复现脚本及依赖版本留在项目，Python 使用工作区专用 Conda。

完成报告分别说明提取、实现、原版一致性、人工/平台验收。存在关键未知或占位功能时，不以构建成功、资源数量或测试数量宣布全功能重建完成。
